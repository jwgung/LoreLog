# 0007. 임베딩은 질문에 맞는 건을 찾고, 같은 거래처의 다른 건은 거래처와 최근 순으로 모은다

- 상태: 채택 (2026-11-03). [ADR 0006](0006-precedent-by-topic-and-counterparty.md)의 "지금 일을 추정하지 않는다"(일부)와 "로컬 임베딩 재검토"를 **대체**한다. 0006의 나머지는 그대로다.
- 결정한 사람: 사용자
- 티켓: https://github.com/jwgung/LoreLog/issues/101 (지도 https://github.com/jwgung/LoreLog/issues/91)

## 맥락
ADR 0006은 임베딩 시험을 먼저 하고 도입 여부를 사용자가 정한다고 했다. 개발용 검증 세트 20문항으로 두 가지를 설정을 미리 고정해 한 번씩 쟀다. 임베딩은 사용자 자신의 사설망 모델 서버의 `Qwen/Qwen3-Embedding-4B`(2560차원)이고, 앱이 이미 개인 데이터를 보내는 서버다.

- **질문→건:** 정답 건을 상위 8건에 담은 문항이 임베딩 16/20, 사서 검색과 합친(RRF) 13/20, 사서 말 그대로 10/20이다. "전에 어떻게 했지"만 보면 임베딩 7/10, 합친 것 4/10, 사서 2/10이다.
- **건→건:** 사용자가 고른 지난 건을 정답 건 벡터와 가까운 순으로 찾으면 전체에서 양성 11건 중 2건만 들어왔다. 같은 거래처 풀 안에서는 최근순 상위 3건이 지난 건을 더 잘 올렸다(recall 0.93 대 0.80).
- **해석:** 사용자가 고른 지난 건은 의미가 가장 가까운 메일이 아니라 같은 거래처(같은 프로젝트)의 건이었다. 임베딩의 자리는 지금 일을 찾는 것이고, 지난 건 모으기는 거래처 기준이 맞다.

## 결정
- **질문에 맞는 건은 임베딩으로 찾는다.** 문서는 제목과 본문 앞 1500자, 질문에는 검색 지시문을 붙이고, 건 단위로 접어 상위 8건을 쓴다. 사설망 서버가 없거나 응답하지 않으면 지금의 낱말 검색으로 대신한다.
- **사서 검색과 단순히 합치지 않는다.** 합친 쪽이 임베딩 단독보다 낮았다. 합치는 방식은 구현에서 개발용 세트로 한 가지를 비교해 고르고 시험용 세트로 확인한다.
- **찾은 1위 건에 외부 거래처가 있으면 그 거래처의 다른 건을 더 모은다.** 사용자 참여 먼저, 그다음 최근 순, 최대 3건이다. 임베딩 유사도로는 고르지 않는다. 1위가 사내 일이면 이 단계는 하지 않는다.
- **구분해 밝힌다.** 화면과 답에서 "찾은 건"과 "같은 거래처의 다른 건"을 나누고, 어느 건을 기준으로 삼았는지 한 줄로 밝힌다. 1위가 틀렸을 때 사용자가 알아볼 수 있게 한다.
- **벡터는 색인에 둔다.** 색인은 다시 만드는 사본이라 벡터도 그 안에 넣고 스키마 버전을 올린다. 새 문서가 들어올 때 그 문서만 임베딩한다.

## 결과
- 0006의 나머지 결정(같은 상황 폴백 철회, 지금 일을 가리키는 질문은 되묻기, 평가 방식 변경, 개발용과 시험용 세트)은 그대로이고, 구현은 이 ADR에 맞춘다.
- 모델 낱말과 사용자의 말 그대로를 합치는 검색(0006)은 임베딩 서버가 없을 때의 대체 경로로 남는다.
- 비용은 문서마다 2560차원 벡터(전체 약 56MB)와 새 문서마다 임베딩 호출이다.
- 최종 확인은 구현 뒤 새 시험용 세트로 한 번 한다. 거기서 개발 점수만큼 나오지 않으면 되돌린다.

## 한계
- 개발용 20문항에서 한 번씩 잰 값이라 한 문항이 5%p다. 건→건 시험은 양성 11건(5문항)뿐이다.
- 한 모델, 한 설정, 한 지시문만 썼다. 문서를 1500자로 잘라 뒷부분은 반영되지 않았다.
- 거래처 풀은 "최근순 최대 8개"로 만든 후보라 최근순에 유리한 편향이 있을 수 있다.
- 첨부 문서는 thread 값이 없어 엄격한 판정에서 불리했다. 임베딩으로도 못 찾은 문항이 3개 있었고 공통 특징은 뚜렷하지 않았다.
